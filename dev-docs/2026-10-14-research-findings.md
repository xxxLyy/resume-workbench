## 维度 1 · 引导向导 UX（S5）

### 结论：路线图里「8 步会劝退用户」这个假设，公开证据不支持。

- 步骤数**从不是**被任何研究检验过的变量。流传的「多步劝退」测的是字段总数。`[实证]`
- NN/g 引 CHI（Seckler et al. 2014, DOI 10.1145/2556288.2557265）：符合可用性规范的表单一次提交成功率 **78%**，违规表单 **42%**。**被验证的是字段数，不是步数。** `[实证]`
- NN/g《Wizards》原文告诫的是「切太碎」+「中断不可恢复」，不是「8 步」。同文推荐第 5 条「允许中途退出并保存状态」——**与本项目「可暂存续作」逐字对应**。第 8 条「把上次输入作为默认值」——**与「预填」对应**。`[实证]`
- NN/g《Forms vs. Applications》："Once an online form goes beyond two screenfulls, it's often a sign that the underlying functionality is better supported by an **application**." → **处方是升级成应用形态，不是拆更多步** `[实证]`
- Red Hat/PatternFly 分步 vs 单页对照（n=7）：完成时间与易用性评分「大致相当」，6/7 偏好单页全展。⚠️ **全员完成，未测放弃率**。`[实测]`

### 竞品形态

八家里**只有 Resume.io 真做向导**。Novoresume / Teal / Zety / Enhancv / Reactive Resume 全是「单页分区 + 右侧实时预览」。6/8 把「上传已有简历 / LinkedIn 导入」放落地页主 CTA。

⚠️ 「七家都这样」是相关不是效力（两家是开源，形态被「浏览器本地运行」约束）；**没有任何一家公开过漏斗转化率**。

### 本项目设计对错判定

| 项目设计 | 判定 |
|---|---|
| 可暂存续作 | ✅ NN/g 逐字支持 |
| 只补缺失项 | ✅ NN/g 推荐第 8 条 + Shortest Path |
| **每步可跳过** | ⚠️ **与 NN/g 推荐第 3 条（强制顺序不可跳过）冲突**。这是从业者共识，不是实证。 |
| 8 步结构 | ⚠️ 建议降为 2 屏或单页分区。**但不要宣称这样能降低劝退率**（无数据支持）。 |

### 预填的警告（重要）

> *"correct prefilling enhances compliance. However, in cases of incorrect prefilling, we observe **asymmetric** effects"* —— 预填错了的伤害**不对称**，比手填坏得多。`[实证，付费墙，仅摘要]`

→ 「只补缺失项」必须配套**显眼的逐节复核入口**，不能假设预填对了。

### PDF 导入的坑

- 多栏排版是解析错误头号来源。规则型解析：标准单栏 80–90%，设计型多栏 **40–60%**；视觉模型读图：92–97% / 80–90%。⚠️ **全为厂商技术博客，彼此矛盾，仅定性可用** `[经验]`
- Textkernel：至少 15% 的 CV 用分栏布局 `[实证]`
- LinkedIn 抓取**违反 LinkedIn 服务条款**，且要求用户先手动把字段设为公开 → **本项目不可走这条路** `[实证]`

## 维度 2 · 事实护栏

### 最刺眼的一条

Takano 2026 实测：用户逐条审阅这个人工检查点，对**严重编造**抓得住，对**细微改动**（qualifier 降级、看似合理的新增 claim）**移除率只有约 54.5%**。

→ 把希望寄托在「用户会看出来」上，**一半会漏**。真正的杠杆是**让 diff 在审阅现场就摆在眼前**，不是再加一层模型校验。
⚠️ 出处待核实（已要求 agent 补全标题/arXiv/样本定义，尚未回收）。

### FRANK（NAACL 2021）

人工标注摘要：**60% 至少含一处事实错误**；最高频错误类型之一是 **Entity Error（专名/技术名词/职级被改）**。`[实证]`
⚠️ 完整错误类型分布待回收。

### 技术路线优先级

| # | 手段 | 证据 | 判断 |
|---|---|---|---|
| 1 | 原句锚点从「记录」升级为「强制校验」（模型回填源文本字面子串，程序验证存在） | `[实证]` Slobodkin et al. ACL 2024 (arXiv:2403.17104)：细粒度 span 归因使人工核查耗时降约 50%，准确率持平或更好 | **最高杠杆** |
| 2 | 实体级 diff（专名/技术名词/职级） | `[实证]` FRANK | **当前最大漏洞**，但见下方可行性 |
| 3 | prompt grounding + temperature=0 | `[实证]` Takano 2026：单靠 prompt 护栏降低 86% 编造密度 | 便宜，可做 |
| 4 | 结构不变量（角色数/bullet 条数前后比对） | `[实证]` 「结构突变」是四类失败模式之一 | 纯程序检查，成本极低 |
| 5 | 时序/技术年代校验（LangChain 写进 2018 年岗位） | `[实证]` 失败模式排名第一 | 需技术发布时间表，中等成本 |
| 6 | NLI 蕴含校验 / LLM-as-judge | `[实证弱]` FRANK：高度抽象文本上蕴含类指标相关性掉到 1/4 | **不作为主力** |
| ✗ | 受约束解码作主防线 | `[实证]` | 保证**格式**合法，不保证**事实**为真 |

### ALCE 的重要发现（对「先定锚点再生成」的支持）

Gao et al. 2023 (arXiv:2305.14627)：ChatGPT/GPT-4 在 ELI5 上**约 50% 生成内容未被其引用片段完整支撑**。且「闭卷生成 + 事后补引用」的引用质量**显著变差**。→ **先定锚点再生成 > 先生成再补锚点**。

### 不要降标准

ResumeFlow（SIGIR 2024 Demo, arXiv:2402.06221，唯一同行评审的简历定向生成系统）控制幻觉的指标是 `content_preservation_token`（词袋重合系数）+ `content_preservation_latent`（嵌入余弦相似度）。**该指标会把「把 40% 改成 90%」判为几乎无变化。** 本项目的数字拦截**已显著超过**这条已发表基线。

### 🔧 本地可行性：实体级 diff

**代码事实 `[已验证]`**

| 位置 | 事实 |
|---|---|
| `job.mjs:69` `factGuard` | **18 行纯函数**，2 处调用：`job.mjs:106`（岗位改写）、`zone.mjs:165`（区域改写） |
| 拦截内容 | 仅三条：新增数字 / 丢失日期 / 新增内容含数字 |
| `level` 枚举 | 已是三档 `normal` / `important` / `conflict` |
| 断言位置 | `test-structure.sh:2175` S3-B2 段已有 `factGuard → conflict` 断言 |

**三个设计坑（决定了不能照论文做）**

1. 实体**新增**绝对不能拦 —— 对齐 JD 关键词就是改写的目的本身。
2. 实体**替换**最危险也最难检测。S4a 设计点名的「模型推理延迟」→「系统端到端延迟」，两串无共同 token，集合运算抓不到，要抓需语义比对（不打算加 embedding）。
3. 实体**消失**可能是有意精简（项目全名→简称），硬拦会误伤。

**结论**：只做「实体消失」方向，**只出 warn（`important` 级），不做 conflict，不做替换检测**。实体提取用正则（英文专名 + 中文公司后缀/停用词表），**无新依赖**。代价 **60–80 行 + 断言**。误报率预计不低（中文无分词），所以只能 warn。

## 维度 4 · 中文排版与字体 ⚠️ 含本项目已验证缺陷

### 🔧 已验证缺陷：PDF 字体为 Type 3，体积膨胀 6.9 倍

**调研实测** `[实测]`（macOS + headless shell 153 + playwright-core 1.60）：
- `PingFang SC` → **Type 3**，84KB
- `Heiti/Songti SC` → **Type 0 子集**，12–23KB
- **同内容差 6.9 倍**。原因：PingFang 不在磁盘（dyld 缓存），Chromium 取不到字体流
- 副作用：PingFang 生成的 PDF 跨设备可能换字体

**本项目验证** `[已验证]`：
- `themes/resume-classic.css:5` 字体栈首位 = `"PingFang SC"`
- `pdffonts pdfs/linghaoxiang.pdf` → **全部 Type 3**；2 个字重被拆成 **~20 个独立字体对象**（object 4–21）
- `pdfs/linghaoxiang.pdf` = **1.28MB / 2 页**（源 HTML 正文 45KB）
- `pdftotext` 提取 **8016 字符，中文正确** → **Type 3 未破坏 poppler 文本提取**

**未验证（不得下结论）**：Type 3 是否导致 ATS（Workday/Greenhouse/Lever）提取失败。**等 ATS 调研回收。**

⚠️ **改动约束**：`themes/` 是**冻结件**（`git diff bbbbad60 -- template.html themes/ render.mjs` 必须为空）。改字体栈 = 重设冻结基线，不是随手一行。

### Chromium headless 打印能力边界 `[实测]`

| 属性 | 支持 | 备注 |
|---|---|---|
| `@page {size;margin}` | ✅ | 与 `format` 冲突需 `preferCSSPageSize:true` |
| `page-break-before/after`、`break-before` | ✅ | — |
| `break-inside:avoid` | ✅ | **块高 > 1 页时失效** |
| `orphans` / `widows` | ✅ **真生效**（`orphans:8` 实测首行 50→48） | **可直接用于排版诊断** |
| `line-break:strict` | ✅ 解析 | 对中文标点禁则**无额外效果** |
| `text-autospace` | ✅ 生效（Chrome 139+，默认关） | 中西混排间距 |
| `text-spacing`（简写） | ❌ | 只能用 longhand |
| `text-spacing-trim`（标点挤压） | ⚠️ 解析但无效 | macOS 系统字体上无效果 |
| `hanging-punctuation` | ❌ | 无 CSS 替代 |
| `print-color-adjust:exact` | ✅ | **需显式设**，否则背景被剥离 |
| `unicode-range` | ✅ | 对体积非必需（HarfBuzz 已子集化） |

→ **排版诊断可用的新能力**：`orphans`/`widows` 真生效（标题与正文分离可程序化测量）；`print-color-adjust:exact` 需显式设置（否则强调色丢失）；`text-autospace` 可改善中西混排。

## 维度 5 · 中文语境的特有争议（公众号/长文）

### 公众号 MCP 不可用

本机 `wechat-reader` 桥接不可用（`reachable_cdp: []`，微信 tab 数为 0）。agent 未伪造任何公众号文章标题。结论来自 Exa + SearXNG 的站外中文长文。

### 中文「包装 vs 造假」的底线比英文更硬

牛客网讨论最激烈处：

> 简历包装最多把你从 60 分说成 80 分，底子还在。但「靠 AI 作弊」是通过造假、欺骗把自己从 0 分 P 成 100 分。

差异来源：**国内背调会实打电话核实**，英文市场 reference check 强度弱得多。

### 招聘方一手访谈（最有价值的一条）

104 人资专员侯成纬（台湾）：

> HR 用 **CAR 行为事例法**向下追问，**AI 只能潤飾「單點事項」，無法潤飾「一個層面」**。
> https://blog.104.com.tw/use-ai-to-write-resume/

→ CAR = Situation / Task / Action / Result。**AI 能改单点，改不了整层。** 这条对「局部重生成 vs 整体重写」的产品决策有直接含义。

### 「AI 味」识别的是模板味，不是 AI 本身

> 目前的 ATS 不检测「是否为 AI 生成」。但 HR 肉眼可能识别——如果简历读起来像「AI 味」（大量套话 + 完美但空洞的表达）。
> 被识别的原因很具体：堆「负责」「协助」「参与」等弱动词，缺数字和具体情境。

### 同行的三层防线实践（可直接借鉴）

TRAE 社区一位开发者做简历定制 Agent，最在意「Agent 绝对不能编造经历」，结论是**光靠提示词约束不住**：

> 让 Agent「不虚构」比「会生成」难得多。光靠提示词约束不住，最后是让 TRAE 实现了三层防线——锁定字段校验、数字溯源（无出处的句子直接删）、内容来源引用。

硬约束清单：**数字、时间、公司、学校是锁定字段**，模型改动会被强制恢复原文；**每条内容必须注明来源**；无证据句子直接删并标记「待确认」。
https://forum.trae.cn/t/topic/182470

⚠️ 与本项目现状高度重合 —— 本项目已有「数字/日期拦截 + 原句锚点」，**缺的是「锁定字段强制恢复原文」**（当前只提示，不恢复）。

### 国内实测的一个数据（商业倾向）

某横向评测（厂商自建站，测试由自家工具出镜）：AI简历姬虚构 LLM/RAG/TensorFlow 经历和「带领 2 人测试小组」，面试必翻车。

### 中文市场特殊约束（英文简历里不存在的）

应届生身份、校招一次性、**35 岁门槛**、照片、性别、年龄、学历。国内简历筛选受《就业促进法》第 26 条、《个人信息保护法》第 28 条约束。

### 查不到

**没有任何一篇中文文章专门实测「大模型在简历改写中的幻觉率」。** 这个空白是真的。
国内「AI 工具推荐」多为同一批厂商通稿洗稿（结论与数据完全一致 = 同一份素材分发多域名）。

## 维度 6 · AI 效果评测方法

### 三条决定性证据

**一、单向指标奖励沉默。** 预印本 *Precision Is Not Faithfulness*（arXiv:2606.09376）证明：无参照忠实度指标只测 precision（说了的话是否有据），因此**奖励弃答**——一个把所有成绩删干净的改写可以拿近乎满分。对简历工具是致命的，因为「删掉所有量化业绩」正是最容易被判官放过的坏改写。`[实证]`

**二、自由文本的语义比对误报极高。** ICSME 2025（arXiv:2511.02108，56 万次测试）：人工复核 967 次变形预言机违反，**真阳率仅 62%**；误报最集中的两个任务正是 QA 和 RE——**都是自由文本输出**。→ **不要用 LLM 语义比对做质量门禁**。`[实证]`

**三、LLM 判官在简历领域被直接测过。** NAACL 2025 Findings（aclanthology 2025.naacl-findings.270，**736 份真实简历**）：GPT-4 评分与人工判断「仅轻微相关」，即便做了提示工程优化，最高精确匹配率也只有 **61.61%**。`[实证]`

### 推荐的三层门禁形态

```
第 0 层：确定性集合不变量（正则 + 集合运算，零成本，零 LLM 调用）← 主力门禁
        数字双向、专名闭合、时间单调、条目数守恒、非退化下限
第 1 层：语义不变量（每段 2 次 LLM 调用）← 预警器，不是门禁
第 2 层：变形测试（对工具本身，输入翻倍）← 抓管线不稳定，不抓单条输出
```

原则：**能在第 0 层拦掉的，绝不放到第 1 层。**

### 五条结论

**一、「AI 味」是最强共识，且招聘方侧已形成实际筛选动作。** 招聘方原话：简历「全都一个味道」，旧信号（格式、关键词、量化、强动词）全部失效。**这不是抱怨，是筛选逻辑已经改变。**

**二、付费墙是第二大共识，被描述为「人质模式」。** 反复出现的同一细节：花 45 分钟填完，点 Download 才弹 $14.99/月。

**三、ATS 分数被三方（求职者 / 从业者 / 招聘方）共同判定为不可信甚至有害。** 资深 CPRW 直言 Jobscan「几乎单枪匹马传播了关于 ATS 最流行的神话」。多个用户报告高分 + 零回音。

**四、最强的正面信号不在「生成」，在「改 bullet」。**
- 多个用户自发得出同一结论：让 AI 重写单条 bullet 有效，让它重写整份简历有效率下降。
- **一个 20 份投递的对照实验：AI 版 1 回复 vs 手写版 6 回复。**
- r/ResumeTips 评论排序：**Claude > Rezi > RabbitResume > 其余**——免费通用对话模型是实际首选，付费 builder 多数被排在 Claude 之后。
→ **直接支持 S4a 做「局部重生成」而非「整体重写」**；也支持 104 HR 那条「AI 只能改单点」。

**五、本地优先 / 隐私诉求在 Reddit 上没有形成用户侧共识。** 搜遍 privacy / local-first / offline / data uploaded，找到的证据**全部来自开发者和创业者侧**（他们在造本地工具，问有没有需求），**没有一条来自求职者的自发担忧**。
⚠️ **这是对本项目定位的负面证据**：本地优先是产品选择，不是已验证的付费动机。

**四、中文求职人群的实际工作流是「AI 只做文本，工具做排版」。** 没有人用 AI 直接出最终简历。步骤：

3 粘贴进可视化工具排版（Talencat / 速创猫 / Wonder）

BV1F3NmezE5N 的简介里写满了完整提示词模板（5 大模块 + ATS/行业定制/转型/格式），**是唯一可直接抄的干货**。

### 二、编辑器布局：无实证，仅 WCAG 硬约束

三栏窄屏处理、焦点模式、实时预览 vs 保存后预览 —— **全部无实证**。

唯一可用的规范硬约束是 **WCAG 1.4.10 Reflow**：320 CSS px 宽下不得双向滚动。**三栏收成单栏是合规必需，不是优化。**

输入延迟：NN/g 经典阈值 0.1s / 1s / 10s（引 Miller 1968、Card 1991）。**输入路径上的 AI、校验一律不得阻塞回显。**

### 三、WCAG AA 硬指标

| 项 | 数值 |
|---|---|
| 文本对比度 | ≥ **4.5:1**；大字号 ≥ 3:1（18pt 或 14pt 粗） |
| UI 组件/图形对比度 | ≥ **3:1** |
| 目标尺寸 | ≥ **24×24 CSS px**（5 条例外） |
| Focus Visible | AA，必须有可见焦点 |
| **Focus Not Obscured (2.4.11，新)** | 焦点不得被作者内容**完全遮住** —— **三栏 + sticky 头是雷区** |
| Text Spacing (1.4.12) | 用户改行高 ≥1.5em 时不得丢内容 —— 禁止写死行高 |
| Status Messages (4.1.3) | 走 `role="status"`/`aria-live`，且不抢焦点 |

**不必做**：Focus Appearance（AAA）、44×44（移动经验值，非 WCAG AA）。

### 🔧 本地可行性：sticky 头遮挡焦点（已验证违规）

**代码事实** `[已验证]`：

| 位置 | 事实 |
|---|---|
| `server.mjs:594` `.topnav` | `position:sticky;top:12px;z-index:50` |
| `server.mjs:2251` 快照只读横幅 | `position:sticky;top:0;z-index:1000` —— **z-index 更高，风险更大** |
| `scroll-padding` / `scroll-margin` | **全项目零处** |
| `focus-visible` | 5 个文件都有（server 1 / editor-shell 8 / job-panel 2 / ai-panel 1 / zone-panel 1）✅ |
| 硬编码行高 | `1.6`（body）、`1.7`。默认值不违反 1.4.12（该条针对**覆盖**用户设置） |
| 暗色模式 | **零处**（`prefers-color-scheme` / `[data-theme=dark]` 均无） |

**结论**：键盘 Tab 时焦点会被吸到 sticky 导航条（或 z-index:1000 的横幅）底下 → **WCAG 2.4.11 AA 级违规**。
**代价**：`html{scroll-padding-top:…}` 一行。**本轮最便宜的修复之一。**

### 四、中文排版规范：只有两处有数字

- **clreq §6.3.2 标点挤压**：字间标点通常占 1 em；连接号、间隔号、斜线恒占 1/2 em。大陆/香港多数挤压，**台湾多数不挤**。
- **clreq §6.3.3 中英混排**：汉字与西文/数字间**不多于 1/4 em**（上限非下限）。

⚠️ **clreq 没有给行高数值**，§6.4 只定义字面/字幅术语。「中文 1.6–1.8 行高」**无出处**。
⚠️ **中文字体栈无任何规范**，只能算从业者经验。
⚠️ 中英之间加空格出自**中文文案排版指北**——社区约定，**非标准**。

### 五、暗色模式：不值得做默认

- **CHI 2023（n=459）实证：亮色阅读可靠地快于暗色**，且段落读者并未偏好亮色。NN/g 综述：「不建议对普通人群默认切暗色」，长文类应提供开关。
- **对本项目更致命**：交付物是 PDF，打印时浏览器默认白底，**暗色对交付环节零收益**。
- IMWUT 2024：120 个热门 app 里仅 55%/48% 支持暗色，做了也做得不一致。

→ **本项目当前无暗色模式 `[已验证]`。证据支持维持现状。UI 优化预算不要花在这里。**

### 依赖趋势：浏览器渲染是主流两派之一

| 路线 | 谁在用 |
|---|---|
| **Playwright** | Resume-Matcher（playwright 1.63.0） |
| **Puppeteer** | JadeAI（puppeteer-core + @sparticuz/chromium-min） |
| 自研 react-pdf 栈 | RR v6（@formepdf/* + harfbuzzjs + cjk-regex）—— **react-pdf 正在被淘汰** |
| Typst | RenderCV |
| fpdf2 | ResumeForge（纯 Python 服务端） |

→ **本项目的 playwright + HTML→PDF 不是异类，是主流之一。**
⚠️ 代价：JadeAI 需自维护 37KB 的字体子集 —— **与本项目 Type 3 字体问题是同一类成本**。
