## 1. 目标与三步交付

核心任务链：真实 JD → 独立岗位草稿 → 证据与修改清单 → 接受/调整 → 默认两页 PDF。母版不被覆盖；直接编辑、手动草稿、普通导出始终可用；不为清空提示强迫确认与当前任务无关的素材和区域。

三个可独立验收的步骤（每步完成产品仍可用）：
- **第一步·要求与证据**：创建草稿时填「本次定制要求」（折叠高级项）；建立岗位要求—经历证据对应表。
- **第二步·局部生成与审阅**：基于 S3 绑定生成目标区域候选；锁定/手改受保护；有终点的审阅。
- **第三步·检查与导出**：剩余事项分级；排版诊断与页数口径；超页出路；导出记录。

**前置两个独立修复任务**（不混入重构）：F1 首页 PDF 状态口径、F2 区域确认弹窗取消循环（§8）。

## 3. 入口职责定稿【决策 1】

原「岗位匹配」Tab 能力归入「审阅」Tab 的要求—证据表，不再维护独立匹配分析流程。四入口收敛为三职责：

| 入口 | 职责 | 变化 |
|---|---|---|
| AI 助手 | 自由提问、解释、表达建议（全文级工具：选区改写/体检） | 不变；引导文案去掉"岗位匹配"跳转 |
| 区域 | 分类确认、段落定位、保留标记、局部处理（S3） | 文案与空态修正（D5）+ F2 |
| 审阅（岗位草稿专属） | 岗位要求、经历证据、修改候选、处理进度、导出准备 | **升级**：内部三段「要求与证据｜修改清单｜导出检查」 |
| 排版 | 独立职责 | 不变 |

- 三入口共用同一套生成（zone.mjs/job.mjs 纯函数）、候选（changes[]）与应用（S2 撤销链路）能力，不各建状态与撤销。
- 旧入口、引导文案、快捷跳转同步调整；**既有岗位草稿与审阅记录保持可访问**（changes/todos 数据不动，仅 UI 归并；岗位匹配 Tab 的历史分析结果无持久数据，无迁移负担）。
- 普通文档不显示审阅 Tab（现状即如此，保持）。

### 4.2 三时态与失效规则（v1.1 分立）

**三时态定义**（一个候选从生成到落地的状态坐标，不可混用）：
- **a. 生成基线（genBaseline）**：任务启动时快照——`genTasks.<kind>.baseHash`（整文哈希）+ 候选各自携带的 `baseSnapshot`（生成时该 zid 的段落文本，存于 change）。
- **b. 应用前状态（preApply）**：用户点「接受」那一刻的正文实况（逐 zid 现查）。
- **c. 应用后状态（postApply）**：`change.origText`（接受前的实际文本快照）与 `change.appliedText`（= after，接受后文本）——**origText 是 b 时态的记录，不是生成基线**。

**候选状态判定（v1.3：多命中集合；`candidatesState(change, ctx)` 纯函数单条输入）**：输入单条 change + 当前正文哈希/zid 文本集/当前 evidence 批次号/素材指纹集/**locked 集合**，输出**命中状态集合**（可多命中，`[]` = ok）：

| 状态 | 判定 | 表现 |
|---|---|---|
| `anchor-gone` 落点消失 | **replace/hide/reorder/zone-rewrite**：zid 不在正文；**add**：插入容器消失（容器 zid 不在正文或目标章节被删——add 的锚点是容器不是新段落，**新段落 zid 尚不存在不构成失效**，接受时才创建并记 `change.newZid`） | 标「目标已删除」，不可接受不可撤回 |
| `batch-stale` 证据批次失效 | evidenceRefs 非空且引用批次 ≠ 当前 evidenceGen | 标「证据已更新，需重新核对」 |
| `ref-stale` 来源失效 | mat 型 ref：hash ≠ 当前素材事实指纹 **或 该素材 factStatus ≠ 'confirmed'（取消事实确认即使内容未变也失效——v1.4）**；para 型 ref：zid 段落文本指纹变化 | 标「来源已变化，需重新核对」 |
| `locked-now` 事后锁定（v1.3 反例8） | pending 且 zid 当前在 locked 集合（生成后才加的锁同样拦截旧候选） | 标「该段已锁定」，不可接受；解锁即恢复可接受 |
| `needs-compare` 待比较 | pending 且**候选目标或依赖变化**：锚点当前文本 ≠ baseSnapshot（v1.4：**只看候选自身锚点**——replace 的 zid、add 的容器、hide 的目标条目、reorder 的起终点条目；整文哈希变化不再触发，无关段落改动不影响本候选）或 evidenceRefs 依赖失效 | 进「待比较」区；接受前走确认门（preApply vs 候选），不覆盖正文【决策 4】 |
| `hand-edited` 已接受后手改 | acceptedAt 存在且 zid 当前文本 ≠ appliedText | 标「已按你的修改调整」【决策 4】 |

- **多命中（v1.3 反例9）**：主标签按上表顺序取第一个命中（展示用），但 change.consistency 落**完整命中集合**；「待核对」清单列出**全部**命中项——单显示一个主标签不得使其他核对要求消失；整体完成条件（§5.3）要求待核对集合为空（多命中全部清零，路径见下）。
- **历史态豁免**：`rejected/superseded` 的候选即使命中状态也**不进待核对清单**（历史记录不无故阻塞完成；anchor-gone 的历史条目仅按原规则不可撤回）。
- **保留当前版本（v1.4 反例10 替换：绑定内容与来源版本）**：命中待核对的候选，用户显式点「保留当前版本」→ change 写入 `resolvedAt` + **`resolvedText`（确认时的段落当前文本）** + **`resolvedRefs`（确认时各依赖 ref 的指纹快照）** → 退出待核对清单（历史可查）。**之后再变化则重新核对**：resolvedText ≠ 该 zid 当前文本，或任一 resolvedRefs 指纹与当前不一致 → 重新进待核对（resolvedAt 保留、状态标「需再次核对」）。
- **候选处理状态机（v1.5 明确）**：`pending` →（接受，经 v1.6 保存协议）`accepted` →（撤回，前置校验）回 `pending`；`pending` → `rejected`（可附原因）→（改主意）回 `pending`；`pending` ⇄ `skipped`；`accepted` →（正文变化）命中 `hand-edited` 待核对 →（保留当前版本）`resolved` →（再变化）回待核对；`rejected/superseded` 为终态历史（豁免待核对计数，rejected 可显式恢复 pending）。
  - **skipped 仅表稍后处理（v1.5）**：不解决冲突——skipped 的 conflict **仍按 pending conflict 参与门控**（阻止导出）；**不计入整体审阅完成**（完成条件把 skipped 与 pending 同视为未决）；UI 文案「稍后处理」。
  - **撤回后的存储状态统一（v1.5）**：撤回 = 正文恢复 + change 回 `pending` + **清空 origText/appliedText/acceptedAt**（不留旧快照误导后续判定），同一保存事务内完成（v1.6 JSON 协议）。
- **影响范围隔离（v1.3 反例3）**：接受/撤回/任何正文变更只重算 candidatesState 按条结果——**落点 zid 集合之外且无 evidenceRefs 依赖的候选必须保持原状态不变**（接受项目 A 不影响项目 B，作验收反例）；任何"整批标记"仅发生在显式重新生成（superseded 既有）。

**正文与审阅状态一致性（v1.3：分层刷新，两层各单一入口）**：
- **正文维度**（anchor-gone / needs-compare / hand-edited / locked-now 的正文部分）：每次 `/save` 在 zoneSync 之后、updateMeta 同一事务内跑 `reviewConsistency(job, newHtml)` 逐条写 change.consistency——UI 只读不判；回滚/撤销/区域改写都经 /save 走同一函数。
- **来源维度**（ref-stale / batch-stale）：**读取时即时计算，不落盘、不依赖正文保存**（v1.3 反例6）——`/job/changes` GET 响应组装时对每条候选的 evidenceRefs 现算素材/批次指纹（素材取消确认但不保存简历时，应用与导出检查仍即时发现来源失效）；计算便宜（指纹已在手），无需缓存。
- 回滚特例：快照恢复后首次保存的 accepted 且命中 hand-edited → 「需重新核对」（历史不清除）；reviewPos 不因回滚清除。

**保存协议（v1.6 重写）——JSON 请求体、整次保存幂等、单事务**：
- **载体与兼容**：新客户端的保存请求 `POST /save?id=` 携带 `Content-Type: application/json`，体为 `{requestId, baseRev, html, ops}`（html 为整页字符串、ops 为操作数组，可为空）；**其他 Content-Type（含旧 HTML 上送）走既有路径**——baseMtime 竞争检测与全部现行为不变，旧文档/旧客户端零影响。
- **幂等（整次保存为单位）**：`job.saveReceipts` 环形保留最近 50 条 `{requestId, contentHash, receipt}`——contentHash = 请求体规范化序列化的 sha1；receipt 含 {mtime, hash, rev, appliedOps 摘要}。**同 requestId + 同 contentHash 重试 → 只返回已存回执，任何文件、版本、快照零重写**；**同 requestId 不同 contentHash → 400 拒绝**。旧路径请求不判重不记录。
- **严格基线**：JSON 请求要求 `baseRev === 当前 meta.rev`（**严格相等**——落后或未来都 409，错误信息区分两种情况；多标签竞争由此覆盖，JSON 路径不再携带 baseMtime）。
- **单一事务流程（v1.6 复审批定顺序：全部校验通过前零写入）**：在既有 rootLock + withDocLock 内——① **请求指纹基于转换前的原始请求内容**计算（未剥离归一的请求体规范化序列化 sha1；重试方重发原文即同指纹）→ ② receipts 判重（同 ID 同内容 → **直接返回回执，不重写正文/元数据/版本/快照**，事务不写）→ ③ baseRev 校验（落后/未来均 409）→ ④ ops 逐条校验（operationId 格式/changeId 存在/action 枚举/状态前置/origText 与当前正文锚点匹配——任一失败**整份 400，正文不保存**）→ **四步全过之后**才 ⑤ 创建旧版快照（既有手动快照）+ 开启 beginTx 写入：剥离归一 html → 正文 atomicWrite → zoneSync → applyOps（operationId 防同请求内重复）→ rev+1 → saveReceipts 记录 → commitTx；**恢复顺序沿用既有**（事务异常时旧正文+旧 meta 副本双恢复，机制不改）。
- **关键反例语义（第六轮裁定）**：接受成功但响应丢失 → 撤回成功（rev 已推进）→ **旧接受请求重试**：requestId 命中 receipts 且 contentHash 相同 → 返回旧回执、**不重放**——正文与状态保持撤回后版本；即使判重路径意外失效，baseRev 也已落后 → 双保险拒绝。
- **载体安全性**：中文、换行、emoji、**含 HTML 注释分隔符（`<!--` / `-->`）的任意文本**经 JSON 字符串编码天然安全（v1.5 注释载体方案已撤）。
- **接口（T3/T8）**：/save 按 Content-Type 分流；saveReceipts 环形维护；applyOps 既有。测试反例四组见计划。

**逐操作类型的目标与撤回前置条件**（v1.1 新增；撤回=revertChange 恢复机制）：

| 类型 | 操作目标 | 撤回的前置条件（不满足则提示原因并拒绝静默执行） |
|---|---|---|
| replace | 单一 zid 段落的文本 | 该 zid 存在 且 当前文本 == appliedText（=未经后续手改）；否则提示「该段已被修改，撤回会覆盖你的调整」并要求确认 |
| add | 指定章节/条目下新增段落（带新 zid） | 新 zid 存在 且 文本 == appliedText；撤回=删除该段 |
| hide | 条目（entry-head）或章节的隐藏标记 | 目标仍处于隐藏态；撤回=恢复显示（积木状态，非文本） |
| reorder | 条目在章节内的位置 | 目标条目存在；撤回=反向移动（若期间用户又排序过，提示「位置已变化」并确认） |
| zone-rewrite（区域改写，S3 通道） | 目标区域内多 zid | 同 replace，逐段校验；任一段不满足则该段跳过并在结果中标注 |

### 4.3 事实护栏：现状更正与程序侧检查（v1.2：guardOps 全操作范围 + 补充事实分离）

**现状更正（v1.0 表述有误）**：`job.mjs` 的 factGuard 目前**只做两项**——replace/add 引入原文没有的数字（NUM_RE）、replace 丢失原文日期（DATE_TOKEN_RE）。「公司/职位/日期/学历不得修改」「锁定段落不改写」等目前仅存在于 prompt 约束，**程序侧没有**。S4a 补齐以下四项程序侧检查（全部落纯函数 `guardOps(ops, ctx)`，evidence.mjs 或 job.mjs 归口，生成/局部生成共用）：

| 检查 | 规则 | 违反处置 |
|---|---|---|
| ① 范围（scope，**v1.2 扩为全操作**） | 局部生成（scope=zone:X）的**每一类**候选都必须落在目标区域内：replace/add 按 zid 或落点章节映射的区域；hide 按目标条目（entry-head zid）所属区域；reorder 的起点与终点条目都必须在目标区域 | 拒绝该候选（解析层丢弃，计数报告「越界 N 条」） |
| ② 锁定 | zid 在 locked 集合（zones[zid].locked===true）；hide 类目标条目内的段落任一 locked 同样拒绝 | 拒绝并列入 skipped（S3 通道既有，统一到 guardOps） |
| ③ 必须保留/受保护（v1.3 反例8：hide 展开到条目集合） | hide 的目标无论是章节还是条目，一律**展开为其包含的条目集合**，与 keepProjects 条目**及集合内任一 locked 段落**求交集 | 交集非空 → 拒绝该 hide，标「包含必须保留/已锁定内容」 |
| ④ 受保护字段 | replace 的 before 中命中的**日期 token**（DATE_TOKEN_RE）与**公司/职位 token**（来自已确认素材 facts.company/role 的精确串匹配）必须在 after 中原值保留 | 强制 conflict，理由「修改了受保护字段」 |

（④ 的公司/职位 token 来自已确认素材 facts——不含 JD 内容，维持 JD 不作为事实来源的边界。）

**事实与表达的关系**【决策 6】保持：结构化事实优先约束表达；素材 brief 与 facts 矛盾 → 提示「事实与表达不一致，请先核对」，不自行选有利版本；无证据保留 todo/none，不据 JD 补造；确定性校验与语义疑点分开呈现，模型判断不包装为已核实。

**覆盖语义三层分离（v1.3 反例5 重写：有据 ≠ 简历已表达）**：
- **来源有效性与表达充分性分离（v1.4）**：两个正交维度——
  - **validity（ref 是否有效）**：mat 型 = 内容指纹匹配 **且该素材 factStatus==='confirmed'**（取消事实确认 → 即使内容未变（hash 相同）该 ref 也失效）；para 型 = zid 段落文本指纹匹配。validity 是 ref-stale 判定的唯一输入。
  - **coverage（简历是否充分表达该要求，v1.5）**：`para` ref 存在**不自动等于 covered**——para 存在只证明"已表达"；充分性由机判决定：para 存在且判充分 → covered；para 存在但判不充分 → thin；**仅有效 mat ref → sourced**。**无有效来源不得标 sourced（v1.5）**：ref 全部失效（hash 变或 factStatus≠confirmed）→ 该条**无有效来源 → todo**（UI 显示「来源已变化，待重新关联」，不是 sourced 也不是 thin）。**解析层校正**：模型输出 covered 但无有效 para ref → 有有效 mat ref 则降 sourced、否则降 todo；模型输出与 ref 实际形态矛盾时以 ref 形态为准。
- **用户补充**（noteConfirmed）：note 是自由文本，**不参与 status 计算**；「确认为证据」= 用户口径的**有据**（归入 sourced 同层展示「有据（依据：你的补充）·简历未表达」），同样不是"简历已表达"；关联到具体 ref 后按机判维度计。
- **展示与统计**：三列分计——「简历已覆盖 N（正文）· 素材有据未表达 M · 待补充 K」；导出检查同口径分列。

## 5. 三步流程设计

### 5.1 第一步：要求与证据

**创建流程**（复用 `/job/create`）：六字段基础表单不变 + `<details>` 折叠「本次定制要求」（默认收起）：重点 chips（从素材 tags 与历史 brief.focus 聚合建议）、必须保留（项目多选）、不希望强调（经历多选）、修改幅度（三档单选，默认 refocus）、页数（默认 2）。存为预设 = localStorage（不进 meta，避免跨设备同步问题）。默认两页、折叠高级项——创建不是长表单。

**证据表生成**：`POST /job/evidence`（新端点，走 LLM）：输入 JD + 已确认素材（facts+表达）+ 正文段落（zones 按区域分组）→ 输出受约束 JSON：
```jsonc
{ "evidence": [ { "req": "要求", "status": "covered|sourced|thin|todo|none",
    "refHints": [ {"type":"mat","id":"m-1"} | {"type":"para","zid":"z3f9a1c2"} ] } ] }
```
**匹配规则（v1.3 反例1：只认请求内 ID，不猜文本）**：prompt 的输入侧就携带程序分配的稳定 ID——素材块每条带其 `id`、正文段落每条带 `zid`；模型返回的 refHints **必须原样返回这些 ID**；解析侧（`parseEvidence`）按 ID 精确匹配（matId 在已确认素材集、zid 在正文）——**title/quote 一律不参与匹配**（两份同名素材、两段相同正文时无歧义）；模型额外返回的标题/引文仅作人类可读展示，与 ID 不一致时展示侧标注「模型描述与来源不符」并按 ID 为准。ID 不在输入集合 → 该 ref 丢弃 + 状态降 todo。refId（证据条目内引用 ID）仍在请求发出前由程序预分配（b<gen>r<n>）。**none 判定仅当"已确认素材与正文中均未匹配"**——模型不匹配≠用户没做过，`none` 文案固定为「当前已确认来源中未找到证据」，允许 note 补充。JD 每条要求来源标注为 JD 本身（UI 小字）。
**替换时点（v1.3 反例2）**：evidence 数组的整批替换与 evidenceGen+1 **只发生在新证据成功落账的同一事务内**；生成失败/取消/超时不碰旧 evidence、旧 evidenceGen 与旧候选（它们的 batch 状态原样保留）。

**facts 进生成**：`buildJobPrompt` 素材块升级——`【素材：标题】事实：公司…/职位…/指标…/贡献…（仅已确认）\n表达：brief/technical`；要求卡进 user prompt；两页目标与 degree 联动（light→精简指令、restructure→重组指令）。审阅建议的「依据」列显示 evidence.ref 可读化（素材标题 + 事实字段原文；页面文案用「事实依据」，不暴露内部字段名）。

### 5.2 第二步：局部生成与审阅

**生成通道统一**【决策 1】：全文生成（`/job/generate` 升级版）与局部重生成共用 `job.mjs` 的 prompt 构建 + `zone.mjs` 解析；局部范围 `scope=zone:<key>` 时 prompt 只带该区域段落（zoneParas）+ 全文摘要（digestOf），`locked` 段落跳过并在结果标注（S3 通道已有）。**解锁只是允许后续生成，不立即替换内容**【决策 4】。

**候选生命周期**：gen-start 时记录 baseHash；候选带 zid/origText；「待比较」条件= baseHash 与当前不一致或该 zid 文本 ≠ 生成时快照——接受「待比较」候选前展示当前正文 vs 候选差异（确认门）。局部重生成只 supersede 同 zone 的 pending，不清其他已接受/已拒绝【任务书】。

**审阅操作**【决策 5】：
- 面板三段自由切换（要求与证据｜修改清单｜导出检查），共用岗位上下文与进度摘要；有未处理建议时恢复上次位置（reviewPos），未生成时优先显示要求与证据【决策 2】。
- 修改清单展示「改哪里（定位）/为什么（reason）/依据什么（事实依据）/影响什么（kind+zone）」。
- 普通表达（normal replace/add）按项目分组批量接受；reorder 批量；**hide/important/conflict 逐条**（分别标识：隐藏经历、可能改变原意、事实冲突）。
- 主操作随阶段变化（浏览→「下一条」；候选待定→「接受」；全部处理→「去导出检查」），同时至多一个橙色主按钮。
- 拒绝原因可选 chips（改变原意/太空泛/过度夸大/不符合我的表达 + 自定义），不必填；反馈进当前任务 prompt（job 的 feedback 块），存长期偏好需用户显式点「记住这个偏好」（localStorage）。
- 筛选：全部/仅重点/仅本次变化（gen=当前 changes 任务的最新生成批次）；上下条 + j/k 键。
- **撤销三层**【任务书】：① 撤销本次操作（S2 统一撤销栈，接受建议 = 程序化 op，既有）；② 撤回某条建议（job-panel revertChange，既有，恢复 origText）；③ 恢复历史版本（快照面板，既有）。三者文案与入口区分：「撤销刚才的操作」/「撤回这条建议」/「查看历史版本」。

### 5.3 第三步：检查与导出

**检查分级**（导出页与审阅 Tab 第三段共用同一纯函数 `exportChecks(job, zones)`——数据级检查无需渲染，两侧随时可算；**排版诊断是渲染级**，只在导出页渲染出 PDF 后基于其文本层运行，审阅 Tab 不显示排版项）：
- **阻止导出**：pending 的事实冲突（conflict 且未处理）——既有门控，保持；不因无关区域未确认阻止普通导出【任务书】。
- **建议核对**：pending 的 important、表达不充分（thin）的证据、来源已变化的证据。
- **风格建议**：pageSuggestions 输出（重复/超长/项目过多）。

**排版诊断**（v1.1 明确四要素）：
- **来源映射**：诊断基于渲染后 PDF 的 pdftotext 文本层（按页分桶）；诊断项 → 正文定位的规则 = 页文本片段与段落文本（归一化空白后）前缀匹配 → 命中则给 zid 定位，**不命中只报页码**、不猜测定位。
- **表述纪律（v1.3：撤销置信度分级）**：诊断项一律以**结构性事实**表述（「标题 X 出现在第 2 页最后 2 行内、其内容位于第 3 页前 3 行」），**不标注高/中置信结论**（分级无测量依据）；所有诊断项统一提示「请以实际渲染核对」；**不做空间占比百分比**（如"18%"——无测量依据），末页内容偏少只作定性提示（「末页内容明显偏少，建议核对是否可并入上一页」）。定位规则不变（文本前缀匹配→zid，不命中只报页码）。
- **参数单位**：字号 pt（当前值与建议值都带单位显示）、行高 = 倍数（无单位比值）、段距 = em（相对字号）；每轮建议步长固定——字号 −0.5pt、行高 −0.05、段距 −0.1em，不做自适应大步。
- **自动迭代范围**：**无全自动连续迭代**。一轮 = 诊断 → 一组建议 → 用户显式点「应用本轮建议并重渲染」→ 重渲染复看（半自动，每轮经用户确认）；上限 3 轮，轮次显示「排版迭代 2/3 轮」。达到上限仍超页 → 出路二选一明示：a) 人工取舍（列出最长的 3 个候选精简项，点击跳转）；b) 超页导出（PDF 正常生成，记录标注「超页导出：N 页」）。
- 最小可读参数下限：字号 ≥10.5pt、行高 ≥1.3、段距 ≥0.4em——**下限内不再给压缩建议**（转人工取舍），防止建议把排版压坏。
- 内容精简与排版调整**分别展示、分别接受**【任务书】；排版建议应用走既有 typo 通道（meta.typo）。

**页数口径**：实际页数只来自渲染（PDF 页数）；编辑器「约 N 页（估算，以导出为准）」保持既有标注；导出记录写实际页数。

**三条件分立 + 两级完成（v1.2：整体完成条件补全）**：

| 门 | 条件（全部机判） | 效果 |
|---|---|---|
| **允许导出** | 无未解决事实冲突（**pending 与 skipped 的 conflict 都算未解决**，跨全部批次） | 解禁「下载 PDF」与「记录已投递」；thin 证据、风格建议、未确认分类、旧批次未处理建议**不阻止**导出 |
| **本轮审阅完成**（gen 级，显示用） | 当前生成批次的全部候选已处理（本 gen 无 pending）且无 pending 冲突 且 正文已保存 | 审阅 Tab 显示「本轮完成」+「去导出检查」引导 |
| **整体审阅完成**（v1.5，job 级） | **跨全部批次**：无 pending 且**无 skipped**（两者同视为未决——skipped 仅表稍后处理，不满足完成）+ 无未解决冲突（**skipped 的 conflict 仍算未解决、仍受门控**）+ 待核对集合为空（处理或「保留当前版本」清零）+ 正文已保存；rejected/superseded 历史不进计数 | 审阅 Tab 头部「审阅完成」总态；仍是状态非强制门（**冲突清零才可导出——skipped 不解冲突**） |
| **可投递**（flow=reviewed，S1 契约不动） | 整体审阅完成 + PDF 非陈旧（staleInfo） | 既有派生条件保持单源；导出动作不自动置 reviewed（用户在导出页确认） |

**导出记录**：既有 exportId/冻结契约上增列：公司、岗位、正文版本（rev+hash）、生成时间、实际页数、超页标记。投递绑定契约不动。

## 6. AI 任务最小可靠性（v1.1：taskId / 原子启动 / 旧回调拒绝）

- **任务对象**：`genTasks.evidence` 与 `genTasks.changes` 各自独立（`{taskId, status, startedAt, baseHash, error, scope}`），互不清除、互不阻塞；取消一个不影响另一个。
- **原子启动**：`POST /job/gen-start?kind=evidence|changes` 在**单次 updateMeta 事务内**完成「读当前状态 → running 则拒绝(409) → 否则生成新 taskId（`t-` + 8 hex）+ 置 running + 记 baseHash + startedAt」——无检查与写入分离的窗口，并发双击只有一个成功。
- **全局并发（v1.4 替换：锁内扫描，不新增持久化顶层字段）**：gen-start 经**新增的全表事务接口 `updateMetaAll(root, mutator)`**（mutator 收到整个 docs-meta 对象，读改写同锁原子——既有 updateMeta 是单文档 patch 的全表版）执行：**在元数据锁内扫描各文档的 `genTasks`**——全库同类 running ≤1、两类合计 ≤2（多文档同时启动受限），超限拒绝并提示「另一文档的任务进行中」；通过则在本文档 genTasks 写入新任务。不引入 `_genRegistry` 等新顶层字段（并发事实从各文档既有数据实时推导）。
  - **事务接口变更（列给 T3/T4）**：tx.mjs 新增 `updateMetaAll(root, mutator)`（与 updateMeta 同锁同原子写，mutator 返回整个新表或 null 表示放弃）；测试：两进程并发 gen-start 只一个成功（同 S1-B 并发丢字段测试形状）、mutator 抛错不落盘。
- **截止时间三点校验（v1.4）**：10 分钟总时限在**启动时**（拒接过期 running 的残留——重启恢复钩子已清，双保险）、**读取时**（/job/changes 组装前扫 genTasks，过期 running 置 error）、**完成回调时**（落账前校验 taskId 且 startedAt 未超限——过期回调不落账）三点执行；超时后用户返回页面即见 error，不存在永挂 running。
- **旧回调拒绝（v1.2：全回调类型）**：**成功、错误、超时三类回调**落账前都在 updateMeta 事务内校验 `genTasks[kind].taskId === 回调携带的 taskId` 且 `status === 'running'`；不匹配（已取消/已被新任务取代/已重启清空）→ **丢弃不落盘**（错误也一样——迟到的旧错误不得污染新任务的状态）。取消/重启后的迟到响应因此不可能污染新状态。
- **超时（双层）**：请求级 = llm.mjs chat fetch 加 AbortSignal.timeout（默认 120s，config 可覆盖）；**任务级总时限**（v1.2）= 任务最长存活 10 分钟（含重试），每次读取任务状态时检查 `startedAt + 10min < now && status==='running'` → 判 error("任务超时")——兜底 status 永久悬挂 running 的任何漏网路径。
- **取消（v1.2：带 taskId）**：`/job/gen-cancel?kind=&taskId=` → 校验 taskId 匹配当前 running 任务才置 cancelled（防止误取消刚接棒的新任务）；在途结果（无论成功/失败形态）被旧回调拒绝规则丢弃。
- **状态展示**：running/done/error/cancelled + startedAt；仅真实阶段文案（「正在生成修改建议」「正在分析证据」），无百分比、无费用。
- **失败重试**：error 态显示原因 + 「重试」（重新 gen-start，scope 保留）。
- **离开找回**：状态在 meta（跨刷新）；编辑器顶部「生成中…」迷你指示可点回审阅 Tab。
- **重启恢复**：服务启动时两任务的 `running → error("应用重启中断，可重试")`（taskId 置 null 使任何在途回调失效）；已落盘的 changes/todos/evidence 不受影响（updateMeta 原子性既有保证）。

## 7. UI 方案

### 7.1 全局（决策 7 落位）

暖色杂志方向不变：奶油底 #F6F1E7、编辑器底 #F0EBE2、墨色正文、#C2410C 主操作；衬线只用于标题类，按钮/表单/列表/长说明无衬线；纸张白色。本轮优先级：按钮层级（主/次/文字/危险/图标五类 + hover/focus/pressed/disabled/loading/error 状态）→ 侧栏可读性（13px/1.6 底线复核）→ 状态反馈（空/加载/失败/过期/部分完成都有态）→ 键盘操作 → 窄屏布局。3D 动效延期；轻量反馈动效（150-200ms transition）保留并支持 reduced-motion。高频 5 个导航 emoji（文档/素材/看板/复盘/设置）换本地 SVG（内联 stroke 风格，currentColor），其余 emoji 后续阶段逐步。
